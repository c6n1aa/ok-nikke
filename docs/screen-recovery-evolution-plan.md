# 界面识别与失败恢复：演进计划

> 创建日期：2026-08-24
> 性质：调研结论 + 实施路线（本文不含代码改动）
> 关联文档：`docs/screen-and-recovery.md`（现行机制说明与开发约束；本文各阶段落地时同步更新它）
> 文档状态：Phase 0/1/2 已实施完成并经终检（分支 feature/screen-recovery-evolution）；Phase 3 维持条件触发、暂不启动

---

## 1. 背景与目标

项目进入开发中期，后续玩法与界面会持续增多。现行「界面识别 + 失败恢复」机制（见 `docs/screen-and-recovery.md`）沉淀于开发早期。本文基于对当前实现与 ok 框架匹配层的逐行调研，回答三个问题：

1. 现状如何判定所处界面、切换时如何导航、失败时如何恢复（§2）；
2. 随界面增多、链路加深，现有方案先在哪些地方失效（§3），其中弹窗/子界面带来的具体影响（§4）；
3. 可选改进/替代方案清单，各自标注是否当前推荐，并按演进顺序给出实施计划（§5、§6）。

**目标**：把演进顺序固定下来，避免在规模压力下即兴重构。

**非目标（本期不做）**：
- 不引入导航状态机/界面图（理由见 §5.8）；
- 不把弹窗、塔卡选择等临时子界面注册为「界面」（理由是维度正交，见 §4）；
- 不改动 venv 内 ok 框架源码——所有扩展落在 `src/` 侧。

## 2. 现状摘要

> 本节与 §3 记录的是改造前（2026-08-24）基线，行号以当时代码为准；实现落地后行号已漂移，查阅时以提交 `30f02de` 之前的版本为基线。

### 2.1 判定：按任务实例的声明式注册表

- 每个任务实例自带 `self.screens`：`register_screen(name, features, keywords, ocr_box)`。模板特征取「与」，OCR 关键词取「或」，两者同时配置再取「与」（`NikkeBaseTask.py:563-602`）。
- 判定入口：`is_screen` 单帧、`wait_screen` 轮询、`assert_screen` 超时抛 `WaitFailedException`、`current_screen` 按注册顺序遍历、首个命中即返回（`NikkeBaseTask.py:621-650`）。
- 当前全仓库共 9 个注册界面：基类 `lobby`；`ArkTask` 3 个（ark / tribe_tower / simulation_room）；`CashShopTask` 1 个（付费商店，OCR 关键词）；`RaidTask` 4 个（coop_page / coop_nikke_select_page / solo_raid_page / solo_raid_battle_team_select_page）。

### 2.2 导航：手写线性转换对

界面间切换没有显式模型，全部是 `wait_click_feature(入口) → assert_screen(目标)` 的成对手写代码（全仓库约 8–10 处，如 `ArkTask.py:75-76,191-192`、`RaidTask.py:86-87,167-168`）；「已在目标页则跳过」也在各流程入口手写（`ArkTask.py:61-76`、`RaidTask.py:77,197`）。

### 2.3 恢复：单一锚点的 try_step 协议

`try_step(入口方法)` 捕获 `WaitFailedException` → 失败截图 → `_recover_to_lobby()`（刷新帧 → `dismiss_all_popups` → 点 `common_home` → `wait_for_lobby(30s)`）→ 整段入口方法从头重试（默认共 3 次）→ 耗尽后抛出或跳过（`NikkeBaseTask.py:652-718`）。长战斗等待走独立的节流轮询 `wait_battle_finish`（240s、3s/帧，只检测 `battle_finish_*` 三个特征，`NikkeBaseTask.py:259-303`）。

## 3. 关键局限（按界面规模增大的失效顺序）

证据均为当前代码。

1. **界面知识按任务实例碎片化。** `screens` 存在实例上，跨任务互不可见：`current_screen()` 只能识别当前任务注册过的界面，失败日志里的「当前界面」常为 `None`；`DebugTask.debug_current_screen`（`DebugTask.py:20-34`）遍历自己实例的注册表——永远只有 `lobby` 一项，调试工具名存实亡。
2. **判定成本随界面数线性增长、无逐帧缓存。** 框架只有模板预处理缓存（`FeatureSet.py:279-298`，按灰度/canny 参数缓存模板），没有按帧缓存匹配结果：`find_one` 每次调用重跑 `matchTemplate`（搜索范围 = 标注框 ± variance，`FeatureSet.py:211-281,266-270`），OCR 每次调用重跑推理（`NikkeBaseTask.py:604-619`）。`current_screen` 逐界面全扫；`assert_screen` 失败路径还要为写日志再全扫一遍。
3. **首命中返回、顺序敏感、无消歧。** `current_screen` 按 dict 插入顺序返回首个命中（`NikkeBaseTask.py:621-626`）；当两个界面的特征成子集关系（同级 tab 页）时稳定误判，spec 不支持负条件/优先级。
4. **恢复只认 `common_home`。** `_recover_to_lobby` 的全部手段 = 清弹窗 + 主页按钮（`NikkeBaseTask.py:659-685`）；深层/无主页按钮界面（战斗加载、结算动画、协同匹配页——coco 里已有 `coop_match_page` 特征但未注册、登录过期）恢复必然失败，且失败前先空转 30s。`common_back` 只出现在正常流程，恢复协议不使用。
5. **重试粒度 = 整个入口方法。** 深层失败（如爬到塔 3）回大厅后整段重跑，靠游戏自身幂等性保证不重复消耗，但导航与等待时间全量重付；`try_step` 不理解进度。
6. **吞点击无局部重试。** 动画期点击被吞是最高频瞬时故障；现状 `assert_screen` 满 10s 超时才走完整恢复循环（约 40s+），缺「未转换则原地补点」的边级机制。
7. **长等待无中断哨兵。** `wait_battle_finish`（240s）、协同匹配（60s）只轮询目标特征，不看断线/维护/过期等致命弹窗，只能等满超时，且失败截图常错过真正的弹窗现场。
8. **判定无防抖。** `is_screen` 单帧判定，动画中间帧闪烁误判；它作为分支条件使用时（如 `_nav_to_ark` 前置判定，`ArkTask.py:62-68`）只能靠流程作者手动「刷新帧再判定」。
9. **注册与 coco 标注漂移只在运行时暴露。** 特征被移除时仅记 warning 并返回 False（`NikkeBaseTask.py:591-593`），无构建期校验。

## 4. 子界面（弹窗等）对判定的影响结论

「子界面」分三类，干扰机制不同。注册判据特征在 2560×1440 画面上的位置（dump 自 `assets/coco_annotations.json`）：

| 用途 | 特征 | bbox (x, y, w, h) | 相对典型模态覆盖区 |
|---|---|---|---|
| lobby 判据 | `ark` | (1696, 929, 80, 80) | 右下区：遮罩变暗，可能仍命中 |
| lobby 判据 | `lobby` | (1242, 1289, 77, 79) | 底栏：多数模态不覆盖 |
| ark 判据 | `ark_tribe_tower` | (1350, 319, 204, 151) | 中上：模态体内 |
| ark 判据 | `ark_simulation_room` | (928, 571, 202, 190) | 中部：模态体内 |
| tribe_tower 判据 | `tribe_tower_mark` | (1214, 109, 85, 62) | 顶栏：模态外（好判据） |
| simulation_room 判据 | `simulation_mark` | (1172, 680, 96, 93) | 正中心：模态体内（劣势仅在恢复期/全局分类场景，见 §5.2 适用性说明） |
| 标题 OCR 区 | `box_sub_pages_title` | (1, 29, 190, 43) | 左上角条：模态外 |
| 恢复依赖 | `common_back` / `common_home` | (26, 1342) / (206, 1343) | 左下底栏 |

> 模态覆盖区取经验值约 x∈[400, 2160]、y∈[200, 1150]（居中弹窗 + 全屏压暗遮罩），落地约定前在实机以好友/邮箱弹窗校准一次即可。

### A 类：模态弹窗（好友/邮箱/公告，叠在父页面上）

真实地影响判定，两个方向都可能：

- **遮挡特征 → 误判「不在该界面」**：ark 的两个判据、`simulation_mark` 都在模态体内，弹窗开着时对应 `assert_screen` 会直接超时，触发一次不必要的完整恢复循环。注意时序：当前流程中这些断言点之前已由 `_nav_*` 系列确保无弹窗（先清弹窗再导航再断言），现状不会触发；该风险显形于「任意时刻的判定」——恢复现场与全局分类，而弹窗恰是这些时刻的常态。
- **压暗但不遮挡 → 误判「在该界面」**（更危险）：`TM_CCOEFF_NORMED` 对均匀乘性变暗基本免疫（模板与图像各自归一化），遮罩下特征常仍命中——实测匹配分会下降，是否命中取决于阈值。由此存在一个确定性缺陷：`_recover_to_lobby` 调 `dismiss_all_popups(clear_condition=lambda: self.is_screen("lobby"))`，而清理循环每轮**先查条件、再尝试关弹窗**（`NikkeBaseTask.py:538-540`）；若 lobby 特征在遮罩下仍命中，第一轮即返回「清理完成」——**弹窗一个没关，恢复却报告成功**，重试流程的第一下点击直接落在弹窗上。

现状对 A 类的防御全靠流程纪律（进流程前先 `dismiss_all_popups`；`_nav_to_ark` 的「刷新→判定→清弹窗→再判定」两段式），判定层本身不感知遮挡。

### B 类：流程内顺序子页面（塔卡/关卡选择、队伍编成、快速战斗确认）

顶替父页面而非叠加，父页面特征消失，`current_screen` 返回 `None`。不注册是刻意约定，正常流程靠特征/相对坐标推进，无影响。差异在异常路径：恢复成败取决于该页有无 `common_home`——塔卡/关卡选择这类常规子页通常有主页按钮，恢复可走通但整段重跑；战斗加载、匹配中（未注册的 `coop_match_page`）等没有，恢复必败。

### C 类：全屏中断页（加载、断线、维护弹窗）

判定与恢复双重盲区：无注册特征、无 `common_home`、长等待期间无人轮询，唯一「处理」是等满超时。对策见 §5.6 中断哨兵。

**结论：不需要把这些注册进界面表；要修的是「判定不感知遮挡」与「恢复只有一招」。** 对应 §5 的前置修复与方案 6。

## 5. 方案清单与推荐判定

总览（详细说明在各小节）：

| 编号 | 方案 | 一句话原理 | 成本/难度 | 当前推荐 |
|---|---|---|---|---|
| 前置-A | 修复清理循环 clear_condition 短路 | 调整「查条件/关弹窗」的顺序 | 极低 | ✅ **立即推荐** |
| 前置-B | 判定特征几何约束约定 | 判据优先边角/顶栏，避开模态覆盖区 | 极低（纯约定） | ✅ **立即推荐** |
| 方案 1 | 集中注册表 + 帧缓存 + coco 静态校验 | 界面知识全局化、按帧去重 | 中 | ✅ **推荐（全部方案的地基）** |
| 方案 6 | spec 扩展：遮挡感知/负条件/优先级/防抖 | 判定维度正交化 | 低-中 | ⚠️ **随方案 1 一并定义 schema** |
| 方案 2 | 守卫式转换原语 `transition()` | 「点击→等到目标」合并成边、原地补点 | 中 | ✅ **推荐** |
| 方案 5 | 长等待中断哨兵 | 轮询同时检测致命弹窗 | 低-中 | ✅ **推荐（可与前后阶段并行）** |
| 方案 3 | 分层恢复：`common_back` 回退链 | 恢复逐级验证、先 back 后 home | 中-高 | ⚠️ **条件触发，暂不启动** |
| 方案 4 | 界面图 + `navigate_to` 状态机 | 声明式导航图、失败重规划 | 高 | ❌ **当前不推荐** |

### 5.1 前置-A：修复 `dismiss_all_popups` 的 clear_condition 短路 ✅ 立即推荐

- **原理**：现清理循环每轮先查 `clear_condition` 再关弹窗（`NikkeBaseTask.py:533-556`），遮罩下特征仍命中时直接「清理完成」。改为「先尝试关闭一个弹窗，再查条件」，或条件满足时要求「本轮已无任何弹窗可关」。
- **适用**：所有走 `_recover_to_lobby` 的恢复路径。
- **优势**：用几行改动消掉 §4-A 的确定性缺陷——恢复「成功但弹窗还在」。
- **成本/难度**：极低（一处循环顺序 + 测试用例调整）。
- **推荐理由**：这是 bug 不是演进，越早修越便宜。

### 5.2 前置-B：判定特征几何约束约定 ✅ 立即推荐

- **原理**：注册界面用的判据特征优先选顶栏/底栏/边缘元素（`tribe_tower_mark` 模式），避免全部判据都落在典型模态覆盖区（约 x∈[400,2160]、y∈[200,1150]），新候选按 bbox 自查。约束的适用对象：(a) 今后新注册的界面；(b) 会参与全局分类或恢复期判定的界面（方案 1/3 落地后，判定时机是失败现场等任意时刻，弹窗此时是常态）；对流程内部、导航后立即执行的断言（断言点前已由 `_nav_*` 确保无弹窗），判据位置不构成问题。约定写入 `screen-and-recovery.md` 的约束节。
- **适用**：今后所有 `register_screen` 与 coco 标注。
- **优势**：零代码消掉 §4-A 方向 1（遮挡误判不在界面）的主要来源；现存唯一落在覆盖区内的判据是 `simulation_mark`，但其唯一使用点（`ArkTask.py:119`，`_nav_to_ark` 导航后立即断言）不在适用范围内，当前用法无问题——登记为 backlog，仅当 simulation_room 日后参与恢复期/全局分类时更换判据，不强制迁移。
- **成本/难度**：极低（文档约定 + 一次实机校准覆盖区数值）。
- **推荐理由**：纯收益；界面越多收益越大。

### 5.3 方案 1：集中注册表 + 帧级缓存 + coco 静态校验 ✅ 推荐（地基）

- **原理**，三个子项：
  1. 新增 `src/screens.py` 集中声明全部界面判定；`NikkeBaseTask.__init__` 合并加载，迁出 ArkTask/CashShopTask/RaidTask 里分散的 `register_screen` 调用；判定语义完全不变。
  2. 帧级结果缓存：以帧身份为 key 缓存 `find_one`/标题区 OCR 结果，同一帧内同特征/同区域不重复匹配。实现时核对 executor 是否已有帧序号可用作 key；没有则在基类包装 `next_frame` 维护单调计数（`TaskTestCase` 静态图场景同样适用）。共享 `box_sub_pages_title` 的标题类界面合并为「一次区域 OCR → 多组关键词比对」。
  3. coco 静态校验：新增测试断言「注册表引用的 features/ocr_box ⊆ `assets/coco_annotations.json` 的 categories」，把特征漂移从运行时 warning 变为 CI 失败。
- **适用**：界面数量向几十增长前的必然基础设施。
- **优势**：消掉局限 1、2、9；`DebugTask.debug_current_screen` 第一次真实可用；是方案 3/4 的前置（全局分类是分级恢复与重规划的地基）。判定语义不变 → 零行为风险。
- **成本/难度**：中（新模块 + 基类改造 + 9 处注册迁移 + 2 个新测试关注点）。
- **推荐理由**：当前规模下成本已可接受，且后续所有方案都长在它上面。

### 5.4 方案 6：spec schema 扩展（遮挡感知 / 负条件 / 优先级 / 防抖）⚠️ 随方案 1 一并定义

- **原理**：spec 增加字段——`when_unobscured`（特征命中且当前无遮罩才算命中，复用遮罩区的低成本检测）、`absent`（列表内特征不得命中，消歧子集重叠界面）、`priority`（`current_screen` 按优先级返回而非注册顺序）、`min_frames`（连续 M 帧命中防抖；框架 `wait_until` 已有 `settle_time` 语义可参考）。
- **适用**：同级 tab 页/共享背景特征的相邻界面出现时（商店、付费商店各分页若日后做跨页断言），以及把「页面身份 vs 是否被遮挡」在机制上分开。
- **优势**：消掉局限 3、8 与 §4-A 方向 2（遮罩下误判在界面）这一类靠纪律维持的隐患。
- **成本/难度**：低-中，但**单独做要迁移两次 spec**；随方案 1 的新 schema 一次性定义到位（字段先定义，遮挡检测可滞后启用）。
- **推荐判定**：不单独排期，并入方案 1。当前只有 1 个 OCR 界面、无重叠特征对，属防御性增强。

### 5.5 方案 2：守卫式转换原语 `transition()` ✅ 推荐

- **原理**：基类新增 `transition(to_screen, click=..., time_out=..., retry_click=2)`：点击 → `wait_screen(to, 短超时)` → 未转换原地补点 1–2 次 → 仍失败才抛携带 from/to 上下文的 `WaitFailedException`。逐步迁移现存约 8–10 处 `wait_click_feature + assert_screen` 对。
- **适用**：全部任务的全部导航边；长加载边（进战斗）支持自定义超时/settle。
- **优势**：吞点击/慢动画这类一次性抖动在边级别消化，不再触发「回大厅整段重跑」（局限 5、6）；导航代码量约减半；失败截图自带转换上下文。
- **成本/难度**：中（一个基类方法 + 迁移 + 对应任务测试更新）。
- **推荐理由**：直接消除最高频故障源的恢复开销，收益/成本比高。

### 5.6 方案 5：长等待中断哨兵 ✅ 推荐（可与其它阶段并行）

- **原理**：集中注册表（方案 1）中新增一组「中断界面」（断线/维护/登录过期弹窗特征）；`wait_battle_finish` 与匹配等 60s+ 等待点每次轮询同时检测这组特征，命中即抛 `WaitFailedException` 子类（如 `InterruptedByDialogException`）——`try_step` 天然兼容。
- **适用**：一切长轮询点。
- **优势**：致命故障从「空转 240s 超时」变成「数秒内带明确原因失败」，失败截图能拍到真正的弹窗（局限 7，§4-C）。
- **成本/难度**：低-中；主要工作是随实机遭遇逐步收集各弹窗的稳定特征并标注进 coco。
- **推荐理由**：独立于其它方案，可随时先做。

### 5.7 方案 3：分层恢复——`common_back` 回退链 ⚠️ 条件触发，暂不启动

- **原理**：`_recover_to_lobby` 从「清弹窗→主页」扩展为逐级验证：① 清弹窗；② 连点 `common_back`（上限 N 次，每次点击后刷新重分类，命中任一已注册界面即停）；③ `common_home`；④（配置开关，默认关）重启游戏兜底。
- **适用**：深层链路失败、无主页按钮界面（局限 4、5；§4-B）。
- **优势**：恢复更快更省（back 比重进链路便宜），覆盖现在必然失败的场景，是方案 4 的前置。
- **成本/难度**：中-高；某些界面的「返回」实为「放弃玩法确认」，乱点有语义风险 → 必须先有全局分类（方案 1）+ 按界面的 back 白/黑名单。
- **推荐判定**：触发条件 = 深层玩法继续增加、或「回大厅整段重跑」的时间成本被实测证明不可接受。未触发不做。

### 5.8 方案 4：界面图 + `navigate_to` 状态机 ❌ 当前不推荐

- **原理**：注册表升级为有向图（节点=界面、边=守卫式转换），`navigate_to(target)` 用 `current_screen` 分类 → 最短路 → 逐边执行；失败时按当前所在界面重规划而非回大厅重跑。业界成熟参照：ALAS 的 Page.check_button+link 页面图、MAA 的 pipeline 任务图。
- **适用**：界面 ≥20、深层流程多、跨任务共享前缀导航成为日常负担时。
- **优势**：恢复 = 重规划、进度保留；新增界面只挂节点与边。
- **成本/难度**：高；NIKKE 大量转换带单向加载动画与随机弹窗，图必须建得保守（弹窗建模为边的前置清理而非节点）；自动规划出错比线性代码难排查。
- **推荐判定**：当前 9 个注册界面下是明确的过度设计，列为远期候选，仅在上述触发条件满足且方案 1/3 已落地后重审。
